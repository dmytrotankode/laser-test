# Як підключити свій метод розрахунку (Метод 4, 5, ...)

Коротка інструкція для розробника, який хоче додати свій алгоритм розрахунку
лінії різу, не чіпаючи нічого з існуючого коду.

## 1. Контракт — єдина жорстка вимога

Ваш метод — це звичайний CLI-скрипт, який сервер запускає окремим процесом:

```bash
python run.py --variant <ім'я> --in <папка> --out <шлях до .LS>
```

- **`--variant`** — ім'я набору (просто рядок, для логів; використовувати
  необов'язково).
- **`--in <папка>`** — сервер САМ складає сюди все, що може знадобитись
  (див. розділ 2 нижче). Читайте файли напряму з цієї папки - жодного
  доступу до нашого сервера/бази вам не потрібно.
- **`--out <шлях до .LS>`** — сюди покладіть готовий результат: звичайний
  текстовий Fanuc `.LS` файл.
- Скрипт має завершитись з **кодом виходу 0** і реально створити файл за
  `--out`. Якщо впав (код ≠ 0) або файлу нема - оператор побачить вміст
  вашого stderr/stdout як текст помилки, більше нічого не станеться
  (жодного краху решти системи).
- Таймаут виконання - 600 секунд.

Якщо вашому методу потрібні власні додаткові параметри (як у Методі 2 -
вибір форми заготовки) - вони прийдуть додатковими флагами `--<name>
значення`, які ви самі оголошуєте (див. розділ 4). Це не обов'язково.

## 2. Що лежить у папці `--in`

| Файл | Що це |
|---|---|
| `back.png`, `left.png`, `top.png` | фото трьох ракурсів (може бракувати якогось, якщо не завантажено) |
| `cam_back.npy`, `cam_left.npy`, `cam_top.npy` | калібрування камер - 7 float: `[rvec(3), position(3), focal_px]`, читається `numpy.load()`. Береться з калібровки рецепта САМЕ ЦЬОГО набору: старі набори — `marker_2026-08-21`, нові (з 14.10) — `marker_2026-09-30`. Якщо в `methods.json` у методу `"wants_recipe": true`, сервер додатково передає `--recipe <назва>` (див. `../README.md`, розділ «Калібровка»); без цього прапорця — лише контракт вище |
| `marks_back.json`, `marks_left.json` | розмітка лінії згину оператором (крок 2) - байтова копія `lines/<ім'я>_<ракурс>.json`: об'єкт `{"points": [[u,v], ...], "variant": ..., "view": ...}`, точки у пікселях фото **в порядку проведення лінії** (не сортувати за x - лінія може бути не монотонною); файлу може не бути, якщо розмітки нема |

Таку папку легко зібрати руками для локального тесту (розділ 5). Зі
`incoming/<name>/` (для `discover.py`) вона НЕ збігається: там інші імена файлів і нема розмітки.

## 3. Куди класти файли

```
service_2021/methods/method4/run.py     <- ваш код
service_2021/methods/method4/...        <- будь-які свої допоміжні файли (еталони, ваги моделі, що завгодно)
```

Дивіться `methods/method3/run.py` як приклад самої підгонки (найпростіший з
наявних методів). Але врахуйте: вбудовані методи історично **не читають
`--in`** — розмітку беруть з `lines/` через `pipeline/line_marks.py`, камери —
з рецепта (`--recipe`). Новому методу краще читати саме `--in`: так він не
залежить від нашої структури папок.

## 4. Як зареєструвати

Додати об'єкт у масив `methods` у `service_2021/calib/methods.json`:

```json
{
  "id": "method4",
  "name": "Метод 4",
  "_desc": "короткий опис для нас, оператор його не бачить",
  "entry": "methods/method4/run.py"
}
```

Якщо потрібні власні параметри (вибір зі списку, як форма заготовки у
Методі 2):

```json
{
  "id": "method4",
  "name": "Метод 4",
  "entry": "methods/method4/run.py",
  "params": [
    {"name": "shape", "label": "Назва для оператора", "type": "select", "options": ["1", "2"]}
  ]
}
```

Після цього метод сам з'явиться у випадаючому списку на кроці 3
інтерфейсу - більше нічого змінювати не треба.

## 5. Як тестувати локально, без нашого сервера

1. Зберіть вручну папку на кшталт `--in` (скопіюйте пару фото + `cam_*.npy`
   з `calib/cameras/<назва калібровки>/` + за бажанням `marks_*.json` = копії
   `lines/<ім'я>_back.json`, `lines/<ім'я>_left.json`).
2. Запустіть:
   ```bash
   python methods/method4/run.py --variant test --in ./моя_папка --out ./result.LS
   ```
3. Відкрийте `result.LS` - звичайний текстовий файл, можна звірити X/Y/Z
   вручну.

## 6. Важливо знати про сам `.LS`

- Перша і остання точка в реальній програмі різання - це зазвичай
  **фіксована "домашня" позиція станка** (підвід/відвід), однакова
  незалежно від пози шолома. Її не потрібно рахувати чи підганяти -
  достатньо скопіювати як є з будь-якого еталонного `.LS`.
- Результат має читатися `ls_points.read_ring` (рядки виду
  `P[n]{ ... X = .. Y = .. Z = .. W = .. P = .. R = .. }`): з нього будується
  сцена і він стає шаблоном для вивантаження. Якщо точок не знайдено —
  розрахунок зупиниться з помилкою.
- `NOMINAL_STANDOFF = 10.0` мм - записані в `.LS` координати це шлях
  СОПЛА, а не лінія різу: `сопло = точка_різу + 10мм * вісь_інструмента`.
  Вісь інструмента - з W/P/R цієї ж точки (Fanuc-конвенція, W і R
  міняються місцями при переведенні в матрицю повороту - не описка).

## 7. Що можна переюзати (необов'язково)

У `pipeline/` вже є готові шматки, якими користуються Методи 2/3 - можна
дивитись як на приклад, або дьоргати напряму:

- `pipeline/geometry.py` - читання `.LS`, кільце різу без підводу/відводу,
  вісь інструмента.
- `pipeline/camera_model.py`, `pipeline/contour_fit.py` - проєкція точок на
  фото, порівняння з розміткою.
- `pipeline/ls_template.py` - запис фінального `.LS` (бере еталонний файл
  як "скелет", міняє лише X/Y/Z, решту тексту не чіпає).

Але це опціонально - якщо у вас повністю свій алгоритм на голому
Python/numpy, досатньо просто надрукувати коректний `.LS` файл у `--out`.
Наш пайплайн нічого не перевіряє ВСЕРЕДИНІ вашого методу.
