# service_5054 — передача проекта (2026-07-25)

Этот файл — точка входа для нового разработчика. Кратко описывает, что
это за проект, что было сделано, что сработало, что не сработало (и
почему), и что делать дальше. Подробности — в файлах, на которые здесь
даны ссылки; этот документ намеренно не дублирует их целиком.

## Что делает проект

Корректирует траекторию лазерной резки военных шлемов на роботе Fanuc.
Заготовка (необрезанная Kevlar-оболочка) фотографируется тремя камерами
(сзади/слева/сверху) на стенде; пайплайн сравнивает её положение с
эталонным (для которого траектория уже откалибрована) и генерирует
скорректированный `.ls`-файл, чтобы резать по факту там, где сейчас
физически находится шлем, а не там, где предполагалось.

## Структура репозитория

- **`main`** — рабочая, стабильная ветка. Эвристический метод: для
  каждой камеры отдельно ищется 2D-трансформация (масштаб/поворот/сдвиг)
  силуэта модели относительно силуэта реального фото, дальше эти три
  измерения комбинируются в 3D-коррекцию.
- **`3d-pose-fit`** — экспериментальная ветка (от `main`, коммит
  `3afdf0e`). Честная 3D-подгонка позы вокруг известного физического
  pivot (макушка/сфера), должна была устранить фундаментальное
  ограничение эвристики. Методологически более правильная (подтверждено
  синтетическим тестом), но на реальных данных пока не обгоняет
  эвристику. Не смержена в `main`, не удалена — держим как рабочий,
  документированный эксперимент.

**ОБЕ ветки только что впервые запушены в GitHub** — до этого вся
работа (включая всё описанное ниже) существовала только локально.

## Что реально исправили и оставили в `main` (хронологически)

1. **Несовпадение разрешения масок** (1024px фото vs 4096px рендер) —
   вызывало обвал `scale≈0.24`. Исправлено.
2. **Захардкоженный `px_to_mm`** — одна константа на все камеры вместо
   индивидуального расчёта по каждой. Исправлено.
3. **`INTER_NEAREST` алиасинг** при 8x уменьшении маски — заменено на
   `INTER_AREA`.
4. **`subprocess.run(["python",...])`** вместо `sys.executable` —
   скрипты падали независимо от способа запуска сервера.
5. **Обнуление коррекции по yaw** (`rz_3d=0.0`) — единственная мера,
   давшая подтверждённый выигрыш на всех 5 наборах. Причина: измерение
   yaw структурно ненадёжно (см. `MEASUREMENT_ACCURACY.md`), попытки
   его использовать (в любом виде) вредили больше, чем помогали.
6. **Откат фикса "пивот в 2D-кадре"** (был логичен сам по себе, но
   эмпирически вредил в сочетании с обнулением yaw — полная таблица
   2×2 в `VALIDATION_LOG.md`).

## Что пробовали и ОТКАТИЛИ (важно не повторять вслепую)

Все — с честной документацией и объяснением механизма в
`MEASUREMENT_ACCURACY.md`:

| Попытка | Результат | Почему не сработало |
|---|---|---|
| Коррекция "рычага" (физическая модель) | Слабый/непоследовательный эффект | Поворот и сдвиг измеряются НЕ независимо друг от друга |
| Знак yaw (переворот) + Y-формула без "сверху" вместе | Хуже на всех 5 наборов | Изолированный синтетический тест ≠ поведение на реальных комбинированных данных |
| Pivot в `step08` → физическая макушка (2 раза, разными способами) | Хуже, особенно на больших углах | Смена pivot без пересчёта трансляции вносит ошибку `~(I-R)·(pivot_old-pivot_new)`, растущую с углом |
| Коррекция pitch (×1.3) | Все 5 наборов чуть хуже | Даже "системная" находка на синтетике не переносится на реальные данные |
| X-формула без "сверху" (по аналогии с Y) | 4 из 5 хуже | Не камера "сверху" целиком плоха — конкретно её `dv`, а не `du` |
| Сегментация: простой порог вместо `rembg` | Реально теряет часть шлема в тени | `rembg` использует семантическое понимание формы, порог — нет |
| Сегментация: GrabCut-уточнение поверх `rembg` | 4 из 5 хуже | Визуально безобидное на одном фото не значит стабильное на всех камерах/наборах |
| Кросс-корреляция контура камеры "сверху" для yaw | Не работает вообще (оценка 0.00° всегда) | Реальный сигнал слишком слаб для этого метода — подтверждено 3 разными техниками (см. ниже) |

## Ветка `3d-pose-fit` — коротко

Полная 3D-подгонка позы вокруг макушки, headless-рендер (`render3d.py`),
IoU/chamfer-метрика (`pose_fit_3d.py`). Синтетический тест: восстанавливает
известную позу с точностью 0.03мм/0.01° — метод математически исправен.
На реальных данных — калибровка камер (в т.ч. без ChArUco, самокалибровка
по 5 известным реальным позам) дала частичный, неоднородный выигрыш; две
попытки взвешенной contour/chamfer-метрики для yaw не сработали.
**Корневая находка**: объективная функция (IoU по силуэту) структурно
слабо ограничивает позу по yaw для этого купола (он слишком близок к
телу вращения) — подтверждено прямым sweep-тестом (±15° по yaw меняют
IoU меньше чем на 1%). Подробности, как возобновить работу — см.
`3D_POSE_FIT_STATUS.md` **в этой ветке**.

## Главный вывод сессии

**Три независимо продуманные техники** (взвешивание contour/chamfer ×2
на ветке `3d-pose-fit`, кросс-корреляция на `main`) не смогли извлечь
надёжный сигнал по yaw из текущих 3 камер. Это сходящееся свидетельство
структурного, а не программного, ограничения. Для дальнейшего
существенного роста точности (особенно по yaw) **вероятно нужно
аппаратное решение** — обсуждалась лазерная линия для камеры "сверху"
(structured light/триангуляция вместо пассивного фото) как наиболее
перспективный вариант. Не реализовано, только обсуждено и
задокументировано в `ROADMAP.md`.

## Рекомендации для продолжения

1. Уточнить у производства реальный допуск для v4/v5 — их шумовой пол
   истины (3.85/4.29мм) уже близок к заявленному допуску ≤4мм, возможно
   не для всех случаев физически достижимо точнее.
2. Дешёвые программные направления для yaw на `main` исчерпаны (см.
   таблицу выше) - дальнейшая работа над точностью yaw, вероятно,
   требует аппаратных изменений (лазерная линия) или принципиально
   иного метода (например, честный 3D-visual-hull + ICP, не пробовали).
3. Гибрид эвристики (`main`) и честной 3D-подгонки (`3d-pose-fit`) —
   единственный из первоначального списка кандидатов, который не
   пробовали вообще - не начат из-за накопленного паттерна неудач на
   более простых идеях, не из-за проверки.
