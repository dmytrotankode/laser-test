# Ветка `3d-pose-fit` — статус и контекст для возобновления

Этот файл — точка входа, если возвращаемся к этой ветке после паузы.
Читать вместе с `KNOWN_ISSUES.md` (пункт [7], корневая причина, из-за
которой эта ветка вообще начата) и `VALIDATION_LOG.md` (все числа).

## Зачем эта ветка

`main` (эвристика: поканемерное 2D-сопоставление силуэтов, шаги 04/06/07)
уперлась в фундаментальный потолок: измеренный 2D-сдвиг силуэта не равен
3D-сдвигу объекта, если объект вращается вокруг точки (макушка/сфера,
~170мм от низа), далёкой от видимого центра силуэта (~0-90мm). Формула
"рычага" (угол × 130-170мм) подтверждена на всех 5 архивных наборах
(z_mm/угол ≈ -2.4 везде, см. `KNOWN_ISSUES.md` [6]/[7]). Точечный фикс
пивота внутри 2D-сопоставления это не убрал — значит, дело не в детали
кода, а в самом подходе. Отсюда решение: заменить 2D-эвристику честной
3D-подгонкой позы вокруг известного физического pivot (макушки), по
аналогии с тем, что уже работает в шаге 02 (STL → LS trim points).

## Архитектура

- `scripts/render3d.py` — headless (без браузера) рендер силуэта: тот же
  pinhole-проекция код, что в `service_5050/step05_project.py`, камеры/
  дистанции/up-векторы сверены напрямую с `web/static/js/main.js` (не с
  комментариями в коде — они оказались устаревшими для камеры "сверху").
  Провалидирован через bounding-box (0.3-1.5% совпадение) и визуальный
  оверлей против `model_mask_*.png` из браузера.
- `scripts/pose_fit_3d.py` — основной скрипт:
  - `load_world_vertices` — STL в мировых координатах (= координаты LS,
    трансформация из `step02_result.json`).
  - `find_apex_pivot` — макушка = центроид вершин в пределах 3мм от
    min world-Z (проверено: радиус сужается до 44.9мм на кончике,
    совпадает с топологией шлема).
  - `calibrate_f_px` — эмпирическая перекалибровка фокусного расстояния
    камеры по реальному эталонному фото (не доверяя слепо числу из шага
    0, см. ниже, зачем).
  - `score_pose` — рендерит кандидата позы во все 3 камеры, считает
    среднее IoU против реальных масок; камеры ФИКСИРОВАНЫ относительно
    эталонного центра (не двигаются с кандидатом позы — это был баг,
    см. ниже).
  - `main` — CLI: `--probe` (ручные точки для sanity-check без
    оптимизации) или полный multi-start Powell (5 стартовых точек).
- `scripts/batch_test_pose_fit_3d.sh` — гоняет все 5 архивных наборов
  подряд (~15-20 мин), печатает точка-к-точке метрику для каждого.
  Использовать: `bash scripts/batch_test_pose_fit_3d.sh [output_file]`.
  Безопасен для `input/photos_current/*.png` — они в git, скрипт сам
  восстанавливает их через `git checkout` в конце.

## Что уже точно работает (провалидировано)

**Синтетический тест с известной позой**: подать в `score_pose` заранее
известные rx/ry/rz/tx/ty/tz, отрендерить этой же функцией "эталонные"
маски, затем попросить оптимизатор найти эту позу с нуля — восстановил
её с точностью 0.03мм / 0.01°. Это подтверждает: сам метод (рендер +
IoU + Powell) математически исправен и не имеет фундаментального бага
в оптимизации/рендере/системе координат. Если что-то идёт не так на
реальных фото — источник в данных (сегментация/калибровка камер), не в
методе подгонки как таковом.

## Хронология находок и фиксов (на реальных фото)

1. **Баг "камера следует за моделью"** (пойман ДО доверия
   оптимизатору, через probe-тест: `tx+5мм` давал ИДЕНТИЧНЫЙ скор
   нулевой позе). Причина: `posed_center` включал кандидатскую
   трансляцию, из-за чего камеры "ехали" вместе с моделью. Фикс:
   камеры строятся один раз от эталонного центра, кэшируются в
   `cam_cache`, никогда не пересчитываются от кандидата.

2. **Артефакт стойки/крепления в маске "left"**, не убираемый старой
   `remove_stand()` (которая вообще только для "back" и работала).
   Найдено через визуальный оверлей (рендер vs реальное фото). Фикс:
   не чинили сегментацию, а добавили `CUTOFF_FRACTION` — обрезка нижней
   части кадра (75% для back/left, 90% для top, доля от bbox самой
   цели, не всего кадра) в `iou_score`.

3. **Калибровка f_px камеры "сверху"** (см. `calibrate_f_px`). Нашли
   визуальным оверлеем нулевой позы (без всякой подгонки) против
   реального фото v1: камеры back/left совпадают по размеру в пределах
   ~1-4%, "top" — на ~7% (рендер крупнее реального фото). Совпадает с
   тем, что старая эвристика сама находила при самопроверке эталона:
   scale=0.924 у top против 0.977/0.981 у back/left — тот же камерный
   баг виден с двух независимых сторон. Причина вероятна:
   `step00_analyze_cameras.py` выводит `f_px` из ПРЕДПОЛАГАЕМЫХ
   физических размера/дистанции камеры "сверху" — если предположение
   чуть неверно, `f_px` неверен на тот же процент, и ничего ниже по
   пайплайну не может это заметить (самосогласовано, но неверно).
   Фикс: `calibrate_f_px` переизмеряет `f_px` напрямую из соотношения
   размеров (рендер на нулевой позе vs `solid_{cam}.png` — реальная
   сегментация эталона, не тестовое фото) и подставляет исправленное
   значение в `cam_cache` перед оптимизацией.

4. **(2026-07-24, после калибровки f_px) Найдена вероятная НАСТОЯЩАЯ
   причина остаточной ошибки: объектив-функция (IoU по 3 силуэтам)
   структурно плохо ограничивает позу по некоторым направлениям** -
   это не баг кода, а следствие геометрии (купол шлема почти
   осесимметричен, асимметрия только в зоне обода/среза - то же
   наблюдение, что раньше объясняло слабый сигнал "рыскания" у камеры
   "сверху" в старой эвристике, [5]). Проверено прямым замером IoU
   вокруг найденного оптимума v1 (`roll=-0.15 pitch=1.95 yaw=-0.32
   tx=-11.06 ty=-10.26 tz=-5.31`, score=0.9346):

   | Возмущение | Score | ΔScore |
   |---|---|---|
   | yaw ±15° (весь диапазон) | 0.9287...0.9346 | **≤0.006** - почти плоско |
   | tx от -41 до +19 (диапазон 60мм) | 0.815...0.935 | плато шириной ~20-30мм у оптимума |
   | tz +10 / -10 | 0.891 / 0.880 | -0.044 / -0.055 - хорошо ограничено |
   | ty +10 / -10 | 0.906 / 0.904 | -0.029 / -0.031 - хорошо ограничено |
   | нулевая поза (без подгонки) | 0.8922 | всего -0.042 от оптимума |

   Т.е. **yaw практически не ограничен** (±15° меняют score на <1%), а
   **tx имеет широкое плато** (≈20-30мм разных tx дают почти одинаковый
   score) - оптимизатор сходится стабильно (несколько стартов дают
   близкие ответы) не потому что нашёл истинную позу, а потому что
   попадает в одну и ту же плоскую "долину", форму которой определяют
   мелкие вторичные факторы (шум сегментации, реальная лёгкая асимметрия
   формы), а не физическая истина. Это объясняет, почему предыдущие два
   фикса (cutoff, f_px) были реальными, но недостаточными: они не могли
   исправить то, что не является их браком - объективная функция сама
   по себе слабо чувствительна к позе в этих направлениях. Также
   объясняет, почему то, что `ty`/`tz` хорошо ограничены, не помогает -
   итоговая точка-к-точке ошибка определяется ВСЕМИ 6 параметрами вместе,
   и слабое ограничение по yaw/tx достаточно, чтобы испортить результат
   целиком.

   **Следствие для направления работы**: дальнейшая охота за калибровочными
   багами (ещё одна камера, ещё один cutoff) даст, по аналогии с
   предыдущими двумя раундами, вероятно ещё один частичный, но
   недостаточный прирост. Настоящий рычаг - добавить объективной функции
   недостающую информацию (веса по зоне обода/среза, где асимметрия
   реально есть; или регуляризация слабых направлений через оценку угла
   из старой эвристики как prior). См. `ROADMAP.md` в `main`.

## Мультипозная калибровка f_px (2026-07-24, `calibrate_cameras_multipose.py`)

Производство подтвердило расстояния камер (2500/1650/2000мм - ровно то,
что уже было зашито) и сказало, что отдельная физическая калибровка
камер уже пробовалась раньше и **сделала хуже** (причина не
разбиралась), а сохранённые калибровочные фото не имеют пересечения
борда между камерами (классическая `cv2.calibrateCamera` с ними
невозможна). См. `ROADMAP.md` "Направление 0" за полным разбором.

Вместо физической калибровки - самокалибровка по архиву: для каждого
v1-v5 есть ТОЧНОЕ соответствие точек между эталонным `.ls` и тем, что
записало производство (не Кабш-приближение) → точная (R,T) поза без
всякой зависимости от фото. Держим эту позу ФИКСИРОВАННОЙ, рендерим
через каждую камеру, подбираем `f_px` (только 3 числа, `dist_mm` не
трогаем) так, чтобы рендер лучше совпадал с реальными сегментированными
фото - сразу по всем 5 наборам (15 view вместо 1 у `calibrate_f_px`).
Задача распадается на 3 независимых 1D-подбора (при фиксированной позе
силуэт каждой камеры зависит только от её собственного `f_px`).

Результат:

| Камера | f_px (step00, 1 поза) | f_px (мультипозная, 5 поз) | Направление |
|---|---|---|---|
| back | 22045.5 | 22341.7 | +1.3% |
| left | 21346.2 | 22495.4 | **+5.4%** |
| top | 22000.0 | 19685.2 | **-10.5%** |

**Важное расхождение**: для "top" оба метода согласны по направлению
(f_px нужно уменьшать), хоть и по разной величине (-6.5% у однопозного,
-10.5% у мультипозного). Но для "back"/"left" - расхождение серьёзнее:
однопозный метод считал их почти правильными (+0.65%/-0.6%), мультипозный
находит заметно другую поправку (+1.3%/+5.4%), причём для "back" даже в
**противоположную сторону** (однопозный предлагал уменьшить, этот -
увеличить). Вероятная причина расхождения: мультипозный метод усредняет
по 5 РЕАЛЬНЫМ тестовым фото (не по одному чистому эталонному), и
наследует их шум/артефакты - в частности, известный неубранный
артефакт стойки в камере "left" (`KNOWN_ISSUES.md`, cutoff-фикс лишь
приблизительно его прячет) мог утянуть калибровку "left" в сторону,
компенсирующую форму артефакта, а не реальную оптику. Не установлено,
какой из двух методов ближе к истине - только эмпирическая проверка
(ниже) может судить.

**Эмпирическая проверка на v1** (само v1 входило в калибровочный набор -
не чистый holdout, см. оговорку выше в файле):

| Состояние | mean точка-к-точке | delta_translation (мм) |
|---|---|---|
| без калибровки f_px | 14.30мм | x=-13.26 y=-8.09 z=-4.78 |
| калибровка по 1 эталонной позе | 12.32мм | x=-11.06 y=-10.26 z=-5.31 |
| **калибровка по 5 реальным позам** | **10.67мм** | x=-0.67 y=-14.81 z=-1.80 |

Улучшение продолжается монотонно (14.30→12.32→10.67), и **`tx` перестал
быть большим и отрицательным** (был -11..-13мм, стал -0.67мм) - это
самый обнадёживающий отдельный сдвиг за все три раунда калибровки. Но
`ty` теперь заметно хуже (-14.81мм, было -8..-10мм), и разброс
точка-к-точке стал шире (min=1.71мм, max=17.64мм - раньше ошибка была
более равномерной ~9-16мм на всех точках). Более широкий разброс между
min/max при похожем среднем обычно означает ошибку по повороту/оси, а
не чистый сдвиг - т.е. характер оставшейся ошибки изменился, не только
её размер. **Итог всё ещё далёк от цели** (эвристика 5.09-6.99мм,
допуск ≤4мм, шумовой пол 2.33мм - см. `ROADMAP.md`).

Механизм: `pose_fit_3d.py` теперь читает
`results/<session>/camera_calibration_multipose.json`, если он
существует, и использует его `f_px_calibrated` вместо вызова
`calibrate_f_px()` (однопозная версия) - см. `main()`.

## Текущий объективный статус (на момент паузы, 2026-07-24)

3D-подход **методологически более правильный** (учитывает реальный
физический pivot, синтетический тест это подтверждает), но на реальных
фото за четыре цикла диагностики (три реальных-но-недостаточных
калибровочных фикса подряд, включая мультипозную калибровку выше, и
находка [4] - структурная слабая ограниченность объективной функции)
**всё ещё в ~1.5-2 раза хуже эвристики** на одном и том же (самом
чистом) наборе v1 (10.67мм против 5.09-6.99мм). Каждый калибровочный
фикс дал реальное, воспроизводимое улучшение (14.30→12.32→10.67), но
темп замедляется, а характер ошибки (судя по возросшему разбросу
min/max) смещается от "чистый сдвиг" к "ошибка по повороту/оси" -
дальнейшая калибровочная охота по той же схеме, вероятно, даст всё
более скромный прирост. Приоритетные направления теперь: добавить
объективной функции сигнал там, где его сейчас нет (yaw, tx - находка
[4] выше), а не искать ещё один калибровочный баг. Детальный список
направлений и решение, куда двигаться - см. `ROADMAP.md` на `main`.

**Более старые кандидаты (актуальны, но ниже приоритетом после находки [4]):**
- Визуальный оверлей КАЛИБРОВАННОЙ (после фикса f_px) подогнанной позы
  против реального фото — сделан только для нулевой позы ДО калибровки.
  Может показать следующий слой ошибки так же наглядно, как показал
  предыдущие два.
- Тот же вопрос калибровки f_px мог существовать не только для "top" -
  back/left были в пределах ~1%, но не проверялось, накапливается ли
  небольшая ошибка там в комбинации с чем-то ещё.
- `CUTOFF_FRACTION` (0.75/0.75/0.90) взят по аналогии со старой
  эвристикой без независимой перепроверки для 3D-подхода - произвольная
  доля может конфликтовать с IoU-метрикой по-другому, чем конфликтовала
  со старым 2D-методом.
- Сегментация current-фото (`step05_segment_current.py`) в принципе не
  менялась под 3D-подход - все её баги/приближения (rembg, морфология)
  наследуются как есть.
- Камера "сверху" в принципе даёт слабый сигнал по рысканью
  (`KNOWN_ISSUES.md` [5], отложено) - актуально и для IoU-подхода тоже,
  не проверялось отдельно.

## Как возобновить

```bash
git checkout 3d-pose-fit
# один набор, быстрый sanity-check без оптимизации:
./venv/Scripts/python.exe scripts/pose_fit_3d.py --session run_20260723_122941 --probe
# полный прогон одного набора (после ручной замены фото в input/photos_current/):
./venv/Scripts/python.exe scripts/pose_fit_3d.py --session run_20260723_122941
# все 5 наборов сразу (15-20 мин, фон):
bash scripts/batch_test_pose_fit_3d.sh /tmp/batch3d_results.txt
```

`run_20260723_122941` — рабочая сессия в `results/`, уже содержит
`step00_cameras.json`/`step02_result.json`/эталонные `solid_*.png` —
переиспользуется для всех тестовых прогонов (это не "текущая" сессия
пользователя, а фиксированная тестовая база).
